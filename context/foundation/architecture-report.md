# Architecture Report — a11y-sdk

## What this project is, and why it's being submitted on a different basis than a typical CRUD app

a11y-sdk is a CLI / static-analysis / build-time developer tool, not an end-user application. It has no login, no user accounts, no database, and no persisted user-editable record in the traditional sense. This is not an oversight to be patched before submission — it's what the project is. The certification's mandatory 10xBuilder checklist requires "a mechanism kontroli dostępu odpowiedni dla typu aplikacji" (access control appropriate to the app type) and sensible CRUD data management for the domain; neither has a natural analog here, and `context/foundation/prd.md`'s Access Control and Data Model sections say so plainly rather than inventing a fake login flow or a CRUD feature to force a checkbox. The certification text itself explicitly invites raising exactly this kind of case with the instructors before assuming a non-standard project qualifies as-is. **A reviewer should treat this as the first thing to resolve, not a footnote** — everything else in this report assumes that conversation happens, one way or another, before this project is evaluated against the standard Builder rubric.

With that stated upfront: the rest of this report is a real point of view on what matters, synthesized from four artifacts — `context/architecture/repo-map.md` (L2), `context/changes/npm-release-strategy/research.md` (L3), `context/architecture/refactoring-plan.md` (L4), and `context/domain/{ubiquitous-language,bounded-contexts}.md` (L5) — not generated from a single prompt and accepted on faith. Each claim below traces to a specific file and was checked against the actual code before being written down.

## What matters most

**The repository's own build pipeline is sound, and one hypothesis that looked like a real problem turned out not to be one.** Going in, the working assumption was that `toolkit/scripts/*.cjs` might be hand-maintained duplicates of `src/*.ts` — a classic drift risk. That's false: `tsup.config.ts` defines a second build target that compiles the four toolkit scripts from their `src/` sources, `package.json` wires it as `build:toolkit`, and CI (`.github/workflows/ci.yml`) runs that build and then hard-checks the output files exist. The `.cjs` files are committed to git *on purpose*, not by mistake — because distribution is `cp -r toolkit/` with no install step, the built output has to be current in the working tree at all times. This is an unusual but coherent inversion of the normal "don't commit build output" rule, and it's correctly wired. Getting this fact right mattered more than any refactor suggestion in this report, because it changes what's actually worth worrying about: not "is the build trustworthy" (it is) but "is everything that flows *into* that build trustworthy."

**The one thing that flows into it and isn't trustworthy today is the Angular version pin, and it's a live bug, not a style nit.** `refactoring-plan.md` item 1: this repository's own `package.json` devDependency pins `@angular-eslint/eslint-plugin-template`/`template-parser` at `^19.8.1` — that's what CI actually tests against. But `toolkit/scripts/setup.sh`, the script a real Angular adopter runs, installs `^18.0.0` and never explicitly installs `template-parser` at all. This is invisible in CI because CI never exercises `setup.sh` against a fresh npm install the way a real user would (the sample apps use a symlinked `.a11y`, bypassing the install step entirely). This is the single highest-priority fix in this report: it's a correctness gap for a real adopter, hiding behind a green CI pipeline, in the framework that already has the most structurally unusual ESLint integration of the four (see below).

**The four-framework story is more asymmetric than the README's tidy table suggests, and that asymmetry is real domain complexity, not accidental complexity.** `bounded-contexts.md` and `ubiquitous-language.md` surface this: React and Vue are "install a conventional ESLint plugin" integrations; Svelte is a bridge to the *compiler's own* diagnostics via `svelte/valid-compile`, not a plugin providing rules; Angular requires manually reconstructing a flat-config object because the upstream package ships in eslintrc shape. Two of four supported frameworks are structurally different from the other two. This is worth naming clearly precisely because it's the kind of fact that's easy to flatten into "we support 4 frameworks" and lose — and it's also exactly why `refactoring-plan.md` concludes that trying to force a shared base across the four `toolkit/config/eslint/*.cjs` files would be the wrong move: the divergence is real, not duplicated boilerplate in disguise. Knowing which kind of complexity you're looking at (essential vs. accidental) is the actual architectural judgment call this report is making, not a coin flip.

## What's lower priority

The three near-duplicate AI-tool stub files at the repo root (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`) are genuinely duplicated content — confirmed identical, character-for-character, to their `toolkit/wrappers/` counterparts — but they're duplicated in a *static* way that isn't currently drifting (nothing has changed either copy recently) and costs little today. It's a real item (`refactoring-plan.md` item 2) worth a cheap CI diff-check so it can't drift silently later, but it's not urgent the way the Angular version pin is. Similarly, the four-switch-statements-for-four-frameworks pattern (`refactoring-plan.md` item 4) is real but only bites if a fifth framework gets added — worth deferring rather than speculatively generalizing now.

## What's next

The most concrete, scoped next step is the release-strategy question researched in `context/changes/npm-release-strategy/research.md`: whether a11y-sdk should become a versioned, released artifact (via GitHub Releases with tagged tarballs, npm publish, or both) instead of pure copy-paste distribution. That research reached a real conclusion, not a shrug: GitHub Releases fits the project's existing distribution philosophy more closely (consumers already pin by copy, not by semver range; nothing currently re-syncs a `.a11y/` folder after initial setup), and can be added with no changes to `toolkit/`'s internal structure — tag from `package.json`'s version, run the existing `build:toolkit`, attach a tarball. npm publish is a larger, more speculative move that would require deciding what "the published unit" even is (today's `package.json` `exports` describe the library, not the toolkit, and nothing currently consumes the library directly). This matters beyond tidiness: it's the concrete next step that would close the 10xChampion "artifact registry" gap — right now there are zero git tags and zero GitHub Releases (both verified empty against the real repository), and that gap exists because no release process has been built yet, not because one was tried and rejected.

The other adjacent Champion-tier gap worth naming here rather than burying in the PRD: there is no AI code-review step anywhere in this project's CI, and all 11 merged PRs on GitHub have zero review comments. That's a separate, smaller gap from the release-artifact one, and this report isn't recommending a specific fix for it — it's flagged so a reviewer doesn't have to rediscover it.

## Summary judgment

This project's core engineering is in reasonable shape — the build pipeline that most needed verifying turned out to be correctly wired, and the framework-integration complexity that looks messy on first read is mostly essential rather than accidental. The real, actionable findings are narrower than a first pass might suggest: one live version-pin bug (Angular), one cheap-to-fix drift risk (the stub files), and one genuinely open strategic question (release strategy) that has been researched but deliberately not resolved unilaterally, because the right answer depends on a product decision (does `.a11y/` ever get re-synced after initial copy?) that belongs to whoever owns this project's roadmap, not to this report. The certification-fit question — whether a CLI tool with no access control or CRUD concept can be fairly evaluated against a checklist written for end-user applications — is the one item in this whole exercise that cannot be resolved by more research or more code reading, and is flagged as such rather than talked around.
