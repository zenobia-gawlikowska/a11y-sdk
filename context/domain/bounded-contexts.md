# Bounded Contexts — a11y-sdk

a11y-sdk's own documentation already describes itself as three independent layers (`README.md`: *"Three layers, each independent"*). That framing maps cleanly onto three bounded contexts — each has its own vocabulary, its own notion of "correctness," its own failure mode, and (mostly) its own code, with only the WCAG-criterion vocabulary and the `Framework` type genuinely shared across all three.

## Context 1 — AI Context Injection

**Purpose.** Give an AI coding assistant (Claude, Cursor, Copilot) the WCAG rules and component-aware ARIA/focus/keyboard patterns it needs to generate accessible code *before* the code is written — not as a check afterward.

**Artifacts.** `toolkit/context.md` (the master document — WCAG 2.1 AA minimum coverage by POUR category, plus component-aware patterns for modal/dialog, form, data table, navigation, toast/alert), the six `toolkit/rules/*.md` deep-dives (focus-trap, aria-state, live-region, keyboard-nav, form-labeling, landmark-usage), and the four `toolkit/wrappers/*` stub files that get copied to a consumer project's root and simply point the AI tool at `context.md`.

**Nature: purely advisory, no enforcement.** This is the most important boundary to state plainly: nothing in this context *checks* whether the AI actually followed the rules. `context.md` and the rules docs are read (or not) by whichever AI tool the developer uses; there is no code here, no test surface, no pass/fail signal. Its only mechanism is that `CLAUDE.md`/`.cursorrules`/`AGENTS.md` reference it (`@.a11y/context.md` or equivalent prose pointer) so a compliant AI tool loads it into context automatically. If a developer's AI tool ignores the reference, or the developer edits a component by hand, this context has no way to notice or object — that's Layer 2 and Layer 3's job.

**What crosses the boundary into other contexts.** The WCAG criterion vocabulary defined here (see `ubiquitous-language.md`) is the same vocabulary Layer 2 and Layer 3 report violations against — a developer who has internalized `context.md`'s "1.1.1 Non-text Content" framing will recognize the same citation in a blocked commit or an audit report. That shared vocabulary is the only real coupling between this context and the other two; no code is shared.

## Context 2 — Pre-commit Enforcement

**Purpose.** Catch static, ESLint-detectable a11y violations in staged files before they're committed, using the framework-appropriate plugin.

**Artifacts.** `src/pre-commit.ts` (built to `toolkit/scripts/pre-commit.cjs`), `src/detect-framework.ts`, `src/config-loader.ts`, `src/rule-filter.ts`, the four `toolkit/config/eslint/*.cjs` flat configs, `toolkit/hooks/pre-commit` (the git hook shim).

**Nature: static and deterministic; blocks on violation.** Given the same staged files, the same framework, and the same config, this context always produces the same result — there's no live browser, no network call, no timing dependency. It runs synchronously inside `git commit` (via `core.hooksPath`), and a violation is a hard stop: the hook exits non-zero, and the commit does not happen unless the developer explicitly overrides with `--no-verify`. This is the only one of the three contexts with a real notion of *blocking* — Context 1 has no mechanism to block anything, and Context 3 (below) reports but does not gate.

**Internal model.** Framework resolution (`detectFramework` → optionally a one-time interactive prompt → persisted choice in `.a11y/config/a11y.config.json`) is entirely local to this context; Context 3 does its own separate, simpler thing (a URL argument, no framework concept at all — axe-core inspects rendered DOM, which has no framework identity by the time it's audited). The config schema (`A11yConfig`) is *owned* by this context in the sense that `config-loader.ts` and `rule-filter.ts` exist to serve it — though per `toolkit/context.md`'s own statement, "the audit script always runs all checks regardless of this config," Context 3 explicitly does not consume this context's configuration at all, despite reading the same file format.

**Boundary with Context 3.** Both contexts maintain their own independent rule-ID → WCAG-criterion map (`WCAG_MAP` in `pre-commit.ts`, `RULE_TO_WCAG` in `audit.ts`) rather than sharing one. This is a real, observed seam, not a hypothesis — the two maps use different keys (ESLint rule IDs like `jsx-a11y/alt-text` vs. axe-core rule IDs like `image-alt`) because the two contexts inspect fundamentally different things (static source AST vs. rendered DOM), so a shared map wouldn't actually eliminate duplication, it would just relocate it. This is a legitimate reason for two contexts to each own their own translation table rather than a coupling to fix.

## Context 3 — Runtime Audit

**Purpose.** Scan a live, rendered page with axe-core and report accessibility violations grouped by WCAG criterion, on demand.

**Artifacts.** `src/audit.ts` (built to `toolkit/scripts/audit.cjs`), which owns both the Playwright browser automation and the `formatResults` reporting logic in the same file.

**Nature: dynamic, requires a live page; advisory, not blocking.** This is the inverse of Context 2 on both axes. It requires a running dev server (`page.goto()` against a real URL) and depends on runtime rendering, JavaScript execution, and computed styles — things static analysis structurally cannot see, which is exactly why `color-contrast` and `live-regions` are inert in Context 2's config (see `ubiquitous-language.md`) but are exactly the kind of thing axe-core *can* catch at runtime (`color-contrast` has a direct entry in `RULE_TO_WCAG`). And unlike Context 2, nothing about this context blocks anything — there is no git hook, no CI gate wired to it in this repository; it is invoked manually (`node .a11y/scripts/audit.cjs <url>`) or conversationally (a developer asking their AI assistant to "audit this page"), and its exit code (0 clean, 1 violations found, 2 generic error, 3 Playwright-not-installed) is meaningful to a script or CI pipeline *if* someone chose to wire it into one, but nothing in this repository currently does.

**Failure mode is distinct and deliberately graceful.** Context 2's failure mode for a missing dependency is a hard error (exit 2, "ESLint not found. Run `bash .a11y/scripts/setup.sh` first"). Context 3 has a dedicated, softer failure mode for its equivalent situation: if Playwright/`@axe-core/playwright` aren't installed, it exits with a distinct code (`3`, not `2`) and prints the exact install commands rather than a bare error — verified in `src/audit.ts` lines 104–118. This reflects a real design difference between the two contexts: Context 2's dependencies (ESLint + a framework plugin) are installed by `setup.sh` as part of onboarding, so their absence is unexpected; Context 3's dependencies (Playwright + axe-core) are deliberately *not* installed by default (stated in the README: "installed in your project, not bundled") because they're heavier and not every consumer needs the audit layer immediately — their absence is an expected, first-run state, not an error state.

## Where the three contexts touch

The only genuinely shared vocabulary across all three is the WCAG criterion numbering (Context 1 teaches it, Context 2 and Context 3 each independently cite it). The only genuinely shared code-level concept is the `Framework` type (`"react" | "vue" | "svelte" | "angular" | "unknown"`), and even that is only load-bearing inside Context 2 — Context 1's wrapper files are framework-agnostic prose, and Context 3's audit script never asks what framework rendered the page it's scanning. There is no shared data store, no shared runtime process, and no context that depends on another being present to function — a consumer could in principle adopt only Context 1 (copy `context.md`, skip `setup.sh`'s hook wiring) or only Context 3 (run the audit script standalone) without the others, which is consistent with the README's framing of the three layers as independent.
