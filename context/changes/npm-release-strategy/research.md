# Research: npm / GitHub Releases strategy for a11y-sdk

## Research Question

a11y-sdk is distributed today entirely by copy-paste: `cp -r toolkit/ <project>/.a11y`, followed by `bash .a11y/scripts/setup.sh`. There is no npm package published, no git tag, and no GitHub Release — `git tag` and `gh release list` both return empty against the real repository. `package.json` exists (`"name": "a11y-sdk"`, `"version": "0.1.0"`) and is a real installable-artifact definition, but nothing currently turns it into a released artifact anyone can pull by version.

This matters concretely for certification purposes: the 10xChampion tier names "artifact registry" — specifically, a list of released versions — as a requirement, and that requirement is currently unmet not because a release process was attempted and rejected, but because none exists. The question is whether it should, and if so, which mechanism fits a copy-paste-distributed dev tool.

## Summary

**There is no single obviously-correct answer here, and forcing one would be dishonest about the trade-offs.** The three live options — npm publish, GitHub Releases with tagged tarballs, or both — solve different problems, and the right choice depends on a question this research surfaces but does not answer: does a11y-sdk want a consumer's `.a11y/` folder to ever be *updated* after initial copy, or is "copy once, own it" a permanent design position? The current README and toolkit design lean toward the latter (config is developer-editable, wrappers are "never overwrite" by convention) but nothing states this as a deliberate versioning philosophy — it reads more like a consequence of not having built a release process yet.

What's clear without more input: **whichever mechanism is chosen, `toolkit/scripts/*.cjs` do not need to change.** They are already real `tsup` build outputs (see `context/architecture/repo-map.md`), committed to git because copy-paste distribution requires it. That part of the pipeline is release-mechanism-agnostic — a release process would consume the same `pnpm build:toolkit` output, not replace it.

## What changes for `toolkit/`'s hand-maintained pieces under each model

Copy-paste-as-is has a property worth naming explicitly: **the entire `toolkit/` directory tree, at whatever commit HEAD happens to be, is always exactly what gets copied.** There is no packaging step, no `files` allowlist decision, no `.npmignore` — the consumer's `cp -r` command *is* the packaging step, and it operates on the working tree directly.

Both release mechanisms below break that property in a small but real way: they require deciding, once, what "the toolkit" means as a versioned unit, separate from "whatever is on disk right now." That decision doesn't require rewriting anything in `toolkit/` — `context.md`, `rules/*.md`, `config/a11y.config.json`, `wrappers/*`, and the four ESLint configs are all already static content or already hand-written config with no build step, so they slot into a packaged artifact unchanged. The only things that need a decision, not a rewrite:

- **`toolkit/scripts/setup.sh`** currently resolves paths via `pwd -L` and `BASH_SOURCE[0]` relative to its own location inside a `.a11y/` folder that assumes it was placed by `cp -r`. Packaging this into a tarball or npm package doesn't break that logic — the script still ends up at `<something>/scripts/setup.sh` relative to `<something>/hooks/` and `<something>/config/` either way — but it does mean the "monorepo check" in Step 1 (`.a11y/ must be at the git root`) now needs to also make sense for however the packaged version gets unpacked into place (npm package `postinstall` vs. manual tarball extraction vs. today's `cp -r`). This is a real but small adjustment, not a redesign.
- **`package.json` itself** currently has no `files` field, no `bin` entries pointing at the toolkit scripts, and its `exports`/`main`/`module`/`types` fields describe the *library* (`dist/`), not the toolkit. If npm publish is the chosen path, either a second package (e.g. `a11y-sdk-toolkit`) or an `npx a11y-sdk init`-style CLI wrapper around the existing `toolkit/` payload would need to be decided — today's `package.json` is not currently shaped to `npm publish` the toolkit as-is; it would publish the *library* (`dist/index.{js,cjs}`), which nothing in the README indicates anyone consumes directly. **This is a real gap, not a nitpick**: "publish to npm" is underspecified until someone decides whether the published unit is the library, the toolkit, or a CLI that fetches the toolkit.

## Semver strategy against the ESLint-9-vs-10 boundary

The ESLint 9/10 incompatibility (`@angular-eslint/template-parser`'s scope manager breaks under ESLint 10 — stated plainly in README.md) is real, current, and external: it is not a bug in this project, it is a compatibility ceiling imposed by an upstream dependency the Angular layer needs. This has a direct semver consequence that's worth stating precisely rather than gesturing at "semver, obviously":

- **A future fix for ESLint 10 support, once `@angular-eslint` resolves its side, is not obviously a patch, minor, *or* major release** under strict semver rules, because the answer depends on what "supporting ESLint 10" costs the public contract. If it's additive (detect ESLint version, branch to a different Angular config shape internally, keep everything else identical) it's a minor. If it requires a peer-dependency-range bump (e.g. widening or narrowing the implicit `eslint: ^9.x` expectation stated in comments across the four `toolkit/config/eslint/*.cjs` files) that changes what a consumer must have installed, semver convention says that's a **major**, even though no *code* the consumer wrote changes — the accepted-environment contract changed. This distinction matters because nothing today captures "eslint ^9.x" as a formal peer dependency anywhere; it's only asserted in code comments (`// eslint must be in the developer's project node_modules` in `pre-commit.ts`, version comments atop each `.cjs` config). A real semver strategy would need that constraint promoted from comment to an actual declared peer dependency range before version numbers on it mean anything enforceable.
- **The four framework ESLint configs age independently of each other and of the toolkit as a whole**, because each pins to a different upstream plugin (`eslint-plugin-jsx-a11y@^6.9.0`, `eslint-plugin-vuejs-accessibility@^2.3.0`+`eslint-plugin-vue`, `eslint-plugin-svelte@^3.0.0`, `@angular-eslint/eslint-plugin-template@^18.0.0` per `setup.sh`'s install commands — note this doesn't even match the `^19.8.1` pin in this repo's own `package.json` devDependency, a live inconsistency worth flagging separately). A single toolkit-wide semver number necessarily conflates "the React config bumped its floor" with "the Svelte config is unchanged" — a consumer on Vue has no way to tell from a single version bump whether anything Vue-relevant changed. This is a real cost of any single-version-number scheme and isn't specific to which release mechanism is chosen; it's inherent to bundling four framework integrations under one version.
- **Practical recommendation, stated as a recommendation and not a foregone conclusion:** start with whole-toolkit semver (one version number covering the entire copied directory) rather than per-framework versioning. Per-framework versioning solves a real problem (see above) but multiplies the release surface by 4 before there's evidence anyone needs that granularity. The ESLint-9/10 boundary specifically should be treated as a major-version line whenever it's crossed, precisely because it changes what must already be installed in the consumer's project — that's the one clear, low-ambiguity call this research can make confidently.

## GitHub Releases vs. npm vs. both

This is a dev-tool distributed by copy-paste to a `.a11y/` folder that a consumer then owns and edits (`a11y.config.json` is explicitly developer-editable; wrapper files are explicitly "never overwrite"). That ownership model is the load-bearing fact for this decision, more than any generic "which is better, npm or GitHub Releases" comparison would suggest.

**GitHub Releases with tagged tarballs fits the current design more closely, for one specific reason:** a consumer who wants a specific pinned version of `toolkit/` today would naturally do `git clone --branch v0.2.0` or download a release tarball and `cp -r` from it — this is a small delta from what they already do (`cp -r toolkit/`), not a new tool or workflow. It also matches how the project already thinks about itself: something you pin by tag or commit, not something you declare as a `^0.2.0` range in a lockfile and expect a package manager to resolve and dedupe. Most consumers of a11y-sdk are not going to `npm update` their `.a11y/` folder the way they'd update a real dependency — nothing currently re-copies or re-syncs it after initial setup, and `setup.sh`'s idempotent-append behavior toward `CLAUDE.md`/`.cursorrules`/`AGENTS.md` is designed around "run this once, maybe run it again safely," not "this runs on every install."

**npm publish buys real things GitHub Releases doesn't, but they're things nothing in this project currently needs:** dependency-manager-native version ranges, `npm view a11y-sdk versions` for discoverability, and — most relevantly to the actual stated pain point — a machine-readable version history that could plausibly satisfy a "released-version list" requirement more legibly than a GitHub Releases page would to an automated check. If the Champion-tier "artifact registry" requirement specifically wants something that looks like a package registry entry rather than a release page, that tips the scale toward npm regardless of the distribution-model argument above — **this is worth confirming against the actual rubric text rather than assumed**, because it changes the recommendation.

**"Both" is not automatically double the work if scoped narrowly.** A GitHub Release can be created from the same git tag npm would publish from, using the same `pnpm build:toolkit` + `pnpm build` output, without requiring the toolkit itself to become an npm-installable unit — e.g., tag `v0.2.0`, attach a `toolkit.tar.gz` build artifact to the GitHub Release, and *separately, optionally* `npm publish` the library package (`dist/`) under its existing `main`/`module`/`exports` shape, which today has no consumer but is already correctly built and typed. This decouples "does the artifact-registry requirement get satisfied" (GitHub Releases, low effort, fits existing distribution philosophy) from "does the library become independently npm-installable" (larger, more speculative, and not something any current user has asked for based on the CI/README evidence). Recommending both, sequenced this way, is a real recommendation, not a hedge — but it depends on confirming what the rubric actually wants (see above), which nobody has done yet in this repo's artifacts.

## Concrete next steps

1. **Confirm what "artifact registry" / "released-version list" means in the actual 10xChampion rubric text** before optimizing for either GitHub Releases or npm specifically — this single fact reorders the recommendation above.
2. **Promote the ESLint version constraint from code comment to a real declared range** (peer dependency or explicit documented floor/ceiling) so that a future "supports ESLint 10" change has an unambiguous semver classification instead of a judgment call.
3. **Reconcile the Angular ESLint plugin version mismatch** between `setup.sh`'s install command (`@angular-eslint/eslint-plugin-template@^18.0.0`) and this repo's own devDependency pin (`^19.8.1`) — orthogonal to release strategy, but it's exactly the kind of drift a real release process with a changelog would have caught, and is itself a small, concrete argument for having one.
4. **Decide, explicitly, whether `.a11y/` is meant to ever be re-synced after initial setup**, or whether "copy once, then it's yours to edit" is a permanent design position. This is the single fact that most changes which release mechanism is worth the effort — if re-sync is never a goal, a lightweight GitHub Releases tagging scheme fully satisfies the artifact-registry gap with minimal new surface area; if re-sync becomes a goal later, that's a much stronger argument for npm's version-range machinery.
5. **If GitHub Releases is chosen (the lower-effort path that fits current distribution philosophy):** wire a release job to `main` pushes that tags from `package.json`'s `version` field, runs `pnpm build && pnpm build:toolkit`, packages `toolkit/` into a tarball, and attaches it to a GitHub Release — no changes needed to `toolkit/`'s internal structure, no new `package.json` fields, and the existing CI artifact-existence check already proves the build output is present before this step would run.
